# Chapter 1: 接收器自适应引擎


欢迎来到 `hw` 项目的入门教程！在本章中，我们将一起探索“接收器自适应引擎”的奥秘。

想象一下，你正在用一根很长的网线连接两台电脑，想要快速传输大量数据。但由于网线本身的特性、周围环境的干扰，或者电脑接口的老化，数字信号在传输过程中可能会变得模糊不清、时序错乱，就像有人说话口齿不清一样。如果接收端无法准确识别这些“走样”的信号，数据传输就会出错，甚至完全失败。

那么，接收端是如何在这种情况下依然能够准确地“听懂”并恢复数据的呢？这就是“接收器自适应引擎”大显身手的地方了！

## 什么是接收器自适应引擎？

**接收器自适应引擎 (Receiver Adaptation Engine)** 是接收器中一个至关重要的控制核心。你可以把它想象成一个经验丰富的乐队指挥。在一个复杂的数字通信系统中，有许多专门负责信号调整的“乐手”，比如：

*   **CDR (Clock and Data Recovery, 时钟数据恢复) 模块**：负责从接收到的信号中提取时钟信号，并对齐数据，确保数据采样的位置是正确的。就像乐队中的鼓手，负责稳定节拍。
*   **FFE (Feed-Forward Equalizer, 前馈均衡器) 模块**：负责补偿信号在信道中产生的部分失真，有点像调音师修正乐器的音色。
*   **CTLE (Continuous Time Linear Equalizer, 连续时间线性均衡器) 模块**：通常用于放大高频信号，补偿信道对高频的衰减，让信号的“高音”部分更清晰。

这些模块（我们将在后续章节 [CDR 自适应](04_cdr_自适应__cdr_adaptation__.md)、[FFE 自适应](05_ffe_自适应__ffe_adaptation__.md)、[CTLE 自适应](06_ctle_自适应__ctle_adaptation__.md) 中详细学习）都有各自的自适应算法。

**接收器自适应引擎的工作就是指挥这些不同的自适应算法模块，按照预先编排好的“乐谱”（即自适应序列）和模式，有条不紊地工作。** 它负责管理整个自适应过程的启动、执行和完成。

它的最终目标是：

1.  **优化接收信号的质量**：让模糊的信号变得清晰。
2.  **适应不同的信道条件**：无论是短线缆、长线缆，还是有噪声干扰的环境。
3.  **适应不同的信号特性**：不同速率、不同编码的信号。
4.  **确保接收器能够稳定可靠地恢复数据**。

## 接收器自适应引擎是如何工作的？

接收器自适应引擎通常不是由最终用户直接操作的，而是作为固件（firmware）的一部分，在系统启动或特定事件（例如，检测到信号质量下降）发生时自动运行。它的工作流程可以概括为以下几个步骤：

1.  **启动**：当需要进行自适应时，引擎被激活。这可能是在设备刚上电、连接建立（例如在[链路训练 (Link Training)](03_链路训练__link_training__.md) 过程中），或者在运行中检测到错误率升高等情况下。
2.  **执行预定序列**：引擎会按照一个预定义的“自适应序列”来逐步调整接收器的各项参数。这个序列就像一份详细的说明书，规定了先调整哪个模块，再调整哪个模块，以及调整的策略。
3.  **协调各模块**：引擎会调用各个子模块（如 CDR、FFE、CTLE）的自适应功能。
4.  **监控与评估**：在调整过程中或调整后，引擎可能会间接或直接地评估信号质量（例如，通过误码率、眼图参数等）。
5.  **完成/迭代**：当达到预设的优化目标，或者完成了所有预定步骤后，自适应过程结束。在某些情况下，如果一次调整效果不佳，引擎可能会重复某些步骤或尝试不同的策略。

## 深入探索：代码中的蛛丝马迹

虽然我们是初学者，但稍微看一下相关的代码片段，可以帮助我们更具体地理解接收器自适应引擎是如何在幕后工作的。我们不会深入每一个细节，而是关注它的大致结构和核心思想。

### 1. 自适应序列：“指挥家的乐谱”

接收器自适应引擎需要知道按照什么顺序执行哪些操作。这个顺序通常定义在一个“序列查找表”（Sequence Look-Up Table, LUT）中。

在 `x812_rel2p1\eth_adapt_seq.c` 文件中，我们可以找到这样一个表：

```c
// 文件: x812_rel2p1\eth_adapt_seq.c

// ... (版权信息等省略) ...
#include "adapt_ctrl.h"
#include "eth_adapt_seq.h"

#pragma data("adapt_seq_lut", DATA)

__attribute__((used)) volatile tAdaptSequenceTable_t gAdaptSequenceTableLut[eMaxAdaptCmd] = {
//      { CMD (命令)                  , Skip (跳过), SW Enable (软件使能) },   /* 序号, 注释 */
        { eAdaptCmd_RunAdapt0to1        , 0   , 0         },   /* 0 */
        { eAdaptCmd_SAROfstFast         , 0   , 0         },   /* 1 */
        { eAdaptCmd_SAROfstSlow         , 0   , 0         },   /* 2 */
        { eAdaptCmd_RunAdapt0to10       , 0   , 0         },   /* 3 */
        // ... 更多自适应命令 ...
        { eAdaptCmd_PostAdaptCcaEnable  , 0   , 0         },   /* 28 */
};
#pragma data() // "adapt_seq_lut"
```

*   `gAdaptSequenceTableLut` 就是这个“乐谱”。它是一个数组，每个元素 `tAdaptSequenceTable_t` 代表一个自适应步骤。
*   `CMD` (命令)：定义了当前步骤要执行的具体操作，比如 `eAdaptCmd_RunAdapt0to1`（运行某个自适应模式组合）或 `eAdaptCmd_SAROfstFast`（执行快速的 SAR 偏移校准）。
*   `Skip` (跳过)：一个标志位，如果为 1，则跳过当前步骤。
*   `SW Enable` (软件使能)：指示该步骤是否由软件更细致地控制（我们暂时可以忽略这个）。

### 2. 引擎的核心逻辑：“指挥家的执行”

引擎的核心逻辑通常在一个主处理函数中，它会遍历上述的序列，并执行相应的命令。我们可以在 `x812_rel2p1\adapt_ctrl_derived.c` 中找到类似的逻辑。

```c
// 文件: x812_rel2p1\adapt_ctrl_derived.c

// ... (其他包含和定义省略) ...

bool processStrupAdaptEth(tRxEthStrupAdapt_t* apEthAdapt)
{
    bool vAdaptAck = false; // 标志自适应是否完成

    if (apEthAdapt->mAwaitAbort) // 如果需要中止
    {
        // ... 中止逻辑 ...
        vAdaptAck = true;
    }
    else if (apEthAdapt->mAdaptTracker >= eMaxAdaptCmd) // 如果所有步骤都完成了
    {
        // 所有启动自适应步骤完成
        apEthAdapt->mAdaptTracker = 0;
        vAdaptAck = true;
    }
    else
    {
        // 自适应正在进行中 - 用 tracker 计数器获取自适应参数
        volatile tAdaptSequenceTable_t* vpStep = &gAdaptSequenceTableLut[apEthAdapt->mAdaptTracker];

        // ... (跳过逻辑检查) ...

        bool vAdaptStateProgressed = false; // 标志当前步骤是否完成

        if (vSkip || vpStep->mSkip) // 如果需要跳过
        {
            vAdaptStateProgressed = true;
        }
        else
        {
            // 执行命令，runCommandGated 会检查一些全局跳过标志
            vAdaptStateProgressed = runCommandGated((uint8_t)vpStep->mCmd);
        }

        if (vAdaptStateProgressed)
        {
            apEthAdapt->mAdaptTracker++; // 进入下一个步骤
        }
    }
    return vAdaptAck; // 返回整个自适应序列是否完成
}
```

*   `processStrupAdaptEth` 函数是自适应引擎的一个主要执行体。
*   `apEthAdapt->mAdaptTracker` 就像一个书签，记录当前执行到“乐谱”的哪一页。
*   它会从 `gAdaptSequenceTableLut` 中取出当前的命令 `vpStep->mCmd`。
*   然后调用 `runCommandGated` (最终会调用 `runCommand`) 来实际执行这个命令。

`runCommand` 函数则像一个分发中心，根据不同的命令调用不同的处理函数：

```c
// 文件: x812_rel2p1\adapt_ctrl_derived.c (片段)

static bool runCommand(enum tAdaptCmd_t aCmd)
{
    bool vDone = false; // 标志当前命令是否执行完毕
    switch (aCmd)
    {
        case eAdaptCmd_RxIdleDetect: // 例如：检测线路是否空闲
        {
            vDone = rxAdaptCtrlDerived_IdleDetect();
            break;
        }
        case eAdaptCmd_SAROfstFast: // 例如：执行快速SAR偏移校准
        {
            vDone = rxSarOffset(true); // true 表示快速模式
            break;
        }
        case eAdaptCmd_RunAdapt0to10: // 例如：运行一组预定义的硬件自适应模式
        {
            // runAdaptModes 会启动硬件执行从模式0到模式10的自适应
            vDone = runAdaptModes(0, 10);
            break;
        }
        // ... 更多 case 处理不同的自适应命令 ...
        default:
        {
            vDone = true; // 未知命令，直接标记为完成
            break;
        }
    }
    return vDone; // 返回当前命令是否完成
}
```

### 3. 自适应模式：“乐章的片段”

某些命令，如 `eAdaptCmd_RunAdapt0to10`，会调用 `runAdaptModes` 函数。这个函数会启动硬件执行一系列预定义的“自适应模式”。这些模式在 `adapt_mode.c` 中定义。

```c
// 文件: adapt_mode.c (片段)

// gModeCtl 定义了多种自适应模式的参数配置
tRxModeCtl_t gModeCtl[eAdaptModeConst_Max] =
{
    { // Mode 1 的配置
        .mFields =
        {
            .mFloatFfeSpeed = 1, // FFE 浮动抽头速度
            .mCdrDlevSpeed  = 1, // CDR DLEV 速度
            // ... 其他模块的速度和使能配置 ...
            .mVgaEn   = 1,       // VGA 使能
            .mMmCdrEn = 1,       // MM CDR 使能
            .mNTop = 400         // 迭代次数或持续时间相关参数
        }
    },
    // ... 其他模式 (Mode 2, Mode 3, ..., Mode 20) ...
};

// initHwAdaptSeq 函数将这些模式配置加载到硬件寄存器中
void initHwAdaptSeq()
{
    // ... (写入 RX__MODE_CTL0 寄存器) ...

    RX__MODE_CTL1_T vRxModeCtl1;
    vRxModeCtl1.mReg = gModeCtl[0].mReg; // 将 Mode 1 (gModeCtl[0]) 的配置
    WRITE_REG(RX_REG_BASE, RX__MODE_CTL1, vRxModeCtl1); // 写入到硬件寄存器 RX__MODE_CTL1

    // ... (为其他模式写入相应的 MODE_CTL 寄存器) ...
}

// startAdaptMode 函数启动硬件自适应模式的执行
void startAdaptMode(uint32_t aStartMode, uint32_t aEndMode)
{
    // ... (一些准备工作，例如设置覆盖使能寄存器) ...

    RX__PIN_OVRDVAL3_T vRxPinOvrdVal3 = READ_REG(RX_REG_BASE, RX__PIN_OVRDVAL3);
    vRxPinOvrdVal3.mFields.INT_RX0_ADAPT_MODE_START_I = aStartMode; // 设置起始模式
    vRxPinOvrdVal3.mFields.INT_RX0_ADAPT_MODE_END_I = aEndMode;     // 设置结束模式
    vRxPinOvrdVal3.mFields.INT_RX0_ADAPT_ABORT_I = 0;             // 清除中止标志
    WRITE_REG(RX_REG_BASE, RX__PIN_OVRDVAL3, vRxPinOvrdVal3);

    // 通过写入寄存器字段来使能自适应过程
    WRITE_REG_FIELD_NEW(RX_REG_BASE, RX__PIN_OVRDVAL3, INT_RX0_ADAPT_EN_I, 1);
}
```

*   `gModeCtl` 数组定义了多达20种不同的“自适应模式”。每种模式都是一组精心配置的参数，告诉硬件中的各个模块（如 FFE、CDR、VGA 等）应该如何协同工作，以何种速度和方式进行调整。
*   `initHwAdaptSeq()` 函数负责在初始化时将这些预定义的模式加载到硬件的相应控制寄存器中。
*   `startAdaptMode(aStartMode, aEndMode)` 函数则告诉硬件从哪个模式开始执行，到哪个模式结束。硬件随后会自动按顺序执行这些模式中定义的自适应操作。

### 4. 辅助工具：“节拍器”

在自适应过程中，某些操作需要等待一段时间，让硬件状态稳定下来，或者让某个调整有足够的时间生效。这时就需要一个计时器。

`adapt_ctrl.c` 文件中的 `adaptWaitTimer` 就是这样一个辅助函数：

```c
// 文件: adapt_ctrl.c (片段)

bool adaptWaitTimer(uint64_t aCycles)
{
    tAdaptWaitTimer_t* vpFsm = &gRx[gActiveLane].mAdapt.mWaitTimer;

    bool vDone = false; // 是否等待完成
    if (vpFsm->mStartCycle == 0) // 如果是第一次调用，记录当前时间
    {
        vpFsm->mStartCycle = rtcRead(); // rtcRead() 读取实时计数器
    }
    else // 如果不是第一次调用，检查时间是否已到
    {
        if ((rtcRead() - vpFsm->mStartCycle) > aCycles) // 如果已过指定周期数
        {
            vDone = true; // 等待完成
            vpFsm->mStartCycle = 0; // 重置起始时间，为下次使用做准备
        }
    }
    return vDone;
}
```

*   这个函数通过读取一个实时计数器 (`rtcRead()`) 来实现等待指定数量的 CPU 时钟周期。
*   这确保了自适应引擎的各个步骤之间有适当的延时。

通过这些代码片段，我们可以看到接收器自适应引擎就像一个调度中心，它读取预设的指令集（自适应序列），然后按部就班地调用各种功能模块（硬件模式、校准算法、等待函数等），最终目的是让接收器达到最佳工作状态。

## 总结

在本章中，我们初步认识了“接收器自适应引擎”。我们了解到：

*   它像一个乐队指挥，是接收器自适应功能的核心控制器。
*   它的目标是协调各种自适应算法（如 CDR、FFE、CTLE 的调整），以优化接收信号质量，确保数据可靠恢复。
*   它通过执行一个预定义的“自适应序列”来工作，这个序列规定了调整的步骤和顺序。
*   代码中通过序列查找表 (`gAdaptSequenceTableLut`)、命令执行函数 (`processStrupAdaptEth`, `runCommand`)、硬件模式配置 (`gModeCtl`) 和辅助函数 (`adaptWaitTimer`) 等共同实现了引擎的功能。

接收器自适应引擎是确保高速通信系统稳定运行的基石。没有它，我们就很难在复杂多变的信道条件下获得清晰可靠的信号。
